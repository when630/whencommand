# WHENCOMMAND — 기술 스펙과 결정 기록

> 프로젝트 정의는 [01_프로젝트.md](01_프로젝트.md), 요구사항 ID는 [02_요구사항.md](02_요구사항.md). 2026-09-19 v0.1.

## 1. 스택 (형제 앱과 동일)

Electron 43 · vanilla JS + CSS(프레임워크 없음) · `node:sqlite` 단일 파일 · electron-builder · 미서명 GitHub Releases + electron-updater.

형제 앱과 다른 점은 **없다.** WHENMUSIC이 네이티브 애드온 하나로 갈라졌던 것과 달리, 이 앱은 Electron 기본 API만으로 전부 된다 — `globalShortcut`, `BrowserWindow`, `shell.openPath`, `child_process`. 런타임 의존성은 `electron-updater` 하나다.

**두 OS를 동등하게 낸다**는 점만 형제 앱과 다르다. 지금까지 다섯 앱은 Windows가 주였고 macOS는 미검증 상태였다([D-13](#d-13-macos를-1급으로-낸다)).

### 식별자

| | 값 |
|---|---|
| appId | `com.when630.whencommand` |
| productName | `WHENCOMMAND` |
| 저장소 | `%APPDATA%\whencommand` · `~/Library/Application Support/whencommand` |
| 스크립트 폴더 | `~/.whencommand/scripts/` (양 OS 공통) |
| 연동 폴더 | `~/.when/apps/` (양 OS 공통, 형제 앱과 공유) |

## 2. 모듈 구조

```
main/
  index.mjs        부트스트랩 (형제 앱과 동일, 8줄)
  lifecycle.mjs    앱 수명 · 트레이 · 전역 단축키 · 창 소유
  panel.mjs        입력줄 창 — 미리 만들고 숨긴다 (D-06)
  place.mjs        창 자리 계산 — 순수 함수 (whenwork 승계)
  ipc.mjs          렌더러 경계
  search.mjs       초성 · 퍼지 매칭 — 순수 함수 (whennote 승계)
  rank.mjs         frecency 점수 — 순수 함수 (D-10)
  manifest.mjs     형제 앱 매니페스트 파싱 · 검증 — 순수 함수
  store.mjs        node:sqlite
  settings.mjs     (형제 앱 승계, 42줄)
  update.mjs       (whenwork 승계, 181줄)
  sources/         결과 공급원 — 전부 같은 모양이다 (D-11)
    index.mjs        등록 · 병합 · 비동기 합류
    apps.mjs         설치된 앱
    files.mjs        OS 인덱스 위임
    calc.mjs         계산 · 단위 변환
    scripts.mjs      셸 스크립트
    siblings.mjs     형제 앱 명령
  platform/        OS 분기는 여기 안에만 (PLAT-01)
    index.mjs · darwin.mjs · win32.mjs
renderer/
  panel.html · panel.js · tokens.css · icons.js
```

`sources/`가 이 앱의 뼈대다. **모든 결과는 같은 모양의 공급원에서 나온다** — 앱도, 파일도, 형제 앱 명령도, 계산 결과도 예외가 아니다. 새 기능은 대개 `sources/`에 파일 하나를 더하는 일이 된다.

```js
// sources/*.mjs 는 전부 이 모양이다
export default {
  id: 'apps',
  ready: async () => {},              // 시작 시 1회. 캐시를 채운다
  query: async (q, ctx) => [item],    // 결과. 느려도 된다 (D-11)
};

// item
{ id, source, title, subtitle, icon, base, run, alt }
//                                    ↑ 0~1 매칭 점수. 최종 정렬은 rank.mjs가 한다
```

                          │
입력 ────────────────────▶ ipc 'query:run'
                          │

                          │                   ├─▶ calc      (즉시)

                          │                   ├─▶ siblings  (캐시. 즉시)
                          │                   └─▶ files     (OS 인덱스. 늦게 도착)
                          │                         │
                          ├─▶ search.mjs  매칭 점수 ◀┘

## 4. 데이터 모델 (v1 스키마)

저장하는 것은 랭킹뿐이다(STOR-02). 검색어 원문은 남기지 않는다 — 무엇을 검색했는지가 아니라 **무엇을 골랐는지**만 필요하다.

```sql
CREATE TABLE picks (
  key       TEXT PRIMARY KEY,   -- 'apps:/Applications/Chrome.app'
  source    TEXT NOT NULL,
  hits      INTEGER NOT NULL DEFAULT 0,
  last_at   INTEGER NOT NULL    -- epoch ms
);
CREATE INDEX picks_last ON picks(last_at DESC);

CREATE TABLE meta (k TEXT PRIMARY KEY, v TEXT);  -- 스키마 버전 등
```

테이블이 둘뿐인 것이 정상이다. 형제 앱의 `store.mjs`가 600~850줄인 반면 이 앱은 100줄을 넘지 않아야 한다 — 넘으면 이 앱이 데이터를 갖기 시작했다는 뜻이고, [01의 원칙](01_프로젝트.md#설계-원칙--형제-앱과의-대칭)이 깨진 것이다.

## 5. 검색과 랭킹 — 이 앱의 핵심 난제

체감 품질의 대부분이 여기서 결정된다. **두 글자를 치면 원하는 것이 첫 줄에 있어야 한다**(SRCH-04).

### 매칭 (`search.mjs`, 순수 함수)

`whennote/main/search.mjs`를 복사해 시작한다. 세 경로를 전부 본다.

| 경로 | 예 | 비고 |
|---|---|---|
| 초성 | `ㅋㄹ` → 크롬 | whennote에 이미 있다 |
| 퍼지(서브시퀀스) | `vsc` → Visual Studio Code | 연속 매칭·단어 첫 글자에 가산점 |
| 자판 오타 교정 | `퍼갸ㅑㅔ` → chrome | 한↔영 자판 매핑 후 재시도 (SRCH-03) |

점수는 0~1로 정규화한다. **연속해서 맞은 구간**과 **단어 첫 글자에서 맞은 것**에 같은 가산점을 준다 — `chr`이 "**C**ache **H**andler **R**unner"의 머리글자 셋보다 "**Chr**ome"의 연속 세 글자에서 높아야 한다(처음엔 연속 가산이 낮아 흩어진 머리글자가 항상 이겼다). 거기에 밀집도(글자가 몇 칸에 몰렸나)와 커버리지(대상을 얼마나 덮었나)를 곱해 정확히 같으면 1이 된다.

### 랭킹 (`rank.mjs`, 순수 함수)

매칭 점수만으로 정렬하면 이름이 짧은 것이 항상 이긴다. 실제로 원하는 것은 **내가 자주 고른 것**이다.

```js
// 최근성 계수 — 버킷으로 끊는다. 연속 함수보다 예측 가능하고 테스트하기 쉽다
const recency = (ms) =>
  ms <   3600e3 ? 4     // 1시간 내
: ms <  86400e3 ? 2     // 하루 내
: ms < 604800e3 ? 1     // 일주일 내
:                 0.4;

// 최종 점수
final = base * (1 + Math.log1p(hits) * recency(now - last_at));
```

`log1p`를 쓰는 이유는 100번 고른 것이 10번 고른 것을 10배로 누르면 안 되기 때문이다 — 새로 설치한 앱이 영영 못 올라온다. 곱셈으로 묶는 이유는 **매칭이 0이면 아무리 자주 골랐어도 나오면 안 되기** 때문이다.

이 두 함수는 Electron 없이 `test/`에서 검증한다. 규칙을 바꾸면 테스트가 먼저 바뀐다.

## 6. 입력줄 창의 제약

| 제약 | 방법 | 확인 필요 |
|---|---|---|
| 120ms 내 표시 | 창을 미리 만들어 `hide()`로 숨겨 둔다. `show()`만 한다 (D-06) | 양 OS 실측 |
| 전체화면 위 | `setAlwaysOnTop(true, 'screen-saver')` + `setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })` | macOS 실측 |
| 포커스 복귀 | macOS `app.hide()` 로 앱 단위 숨김 → OS가 직전 앱으로 돌려준다. Windows는 이전 foreground 핸들을 기억해 복원 | 양 OS 실측 |
| 프레임 없음 | `frame: false, transparent: true, resizable: false, skipTaskbar: true` | — |
| 커서 있는 화면 | `screen.getDisplayNearestPoint(screen.getCursorScreenPoint())` → `place.mjs` | — |

**포커스 복귀(PANEL-06)가 가장 까다롭다.** 두 OS의 방식이 다르고, 이걸 놓치면 앱을 부를 때마다 작업이 끊겨 앱 전체가 쓸모없어진다. `platform/` 안에서 갈라 두고 계약 테스트로 묶는다.

## 7. 명령 규약 (`when-protocol`)

별도 저장소에 둔다([D-12](#d-12-규약은-별도-저장소에-둔다)). 스키마·예제·각 앱이 붙이는 법이 거기 있다.

```jsonc
// ~/.when/apps/whennote.json — 형제 앱이 스스로 떨어뜨린다
{
  "protocol": 1,
  "id": "whennote",
  "name": "WHENNOTE",
  "scheme": "whennote",              // whennote://... 로 부른다
  "verify": {                        // 실제 설치 여부 확인용 (LINK-04)
    "darwin": "/Applications/WHENNOTE.app",
    "win32":  "%LOCALAPPDATA%\\Programs\\whennote\\WHENNOTE.exe"
  },
  "commands": [
    { "id": "new",    "title": "새 메모",   "args": [{ "name": "title", "type": "string", "optional": true }] },
    { "id": "search", "title": "메모 검색", "args": [{ "name": "q", "type": "string" }] }
  ]
}
```

실행은 딥링크 한 줄이다 — `shell.openExternal('whennote://search?q=회의')`. 앱이 꺼져 있으면 OS가 띄워 주고, 떠 있으면 `second-instance`·`open-url`로 기존 인스턴스에 전달된다. 형제 앱은 이미 `requestSingleInstanceLock()`을 쓰고 있어서 받을 준비의 절반은 돼 있다.

**형제 앱이 해야 할 일은 둘뿐이다** — `setAsDefaultProtocolClient(scheme)` 한 줄과, 매니페스트 파일 쓰기. 현재 다섯 앱 모두 딥링크 스킴이 없으므로(2026-09-19 확인) 이 둘을 붙여야 연동이 산다. **붙이지 않아도 그 앱은 그대로 동작한다.**

v1은 딥링크까지만 한다. 결과를 입력줄 **안에서** 보여 주는 라이브 조회(`mode: "live"`)는 양방향 IPC가 필요해 v2로 미룬다([오픈이슈 #2](#오픈이슈)).

## 8. IPC 채널

형제 앱 규약대로 `domain:action`이고, 렌더러는 `contextBridge.exposeInMainWorld('whencommand', …)`로 받는다.

| 채널 | 방향 | 내용 |
|---|---|---|
| `app:init` | invoke | 설정 · 단축키 표기 · 첫 실행 여부 |
| `query:run` | invoke | 입력 문자열 → 즉시 결과 |
| `query:more` | on | 늦게 도착한 공급원의 추가 결과 (D-11) |
| `item:run` | invoke | 항목 실행 → 랭킹 기록 → 창 숨김 |
| `item:alt` | invoke | 보조 동작 (폴더 열기 등) |
| `settings:get` / `settings:autostart` / `settings:openScripts` | invoke | — |
| `hotkey:set` | invoke | 등록 실패를 **돌려준다** (PLAT-02) |
| `update:check` / `update:install` | invoke | — |
| `win:hide` | send | — |

## 9. 테스트 · CI

Electron 없이 도는 순수 함수가 이 앱의 대부분이다 — 형제 앱보다 테스트 비중이 높다.

| 대상 | 검증 |
|---|---|
| `search.mjs` | 초성 · 퍼지 · 자판 교정. 알려진 입력 → 기대 순위 |
| `rank.mjs` | 매칭 0이면 결과 0. 빈도 100 vs 10이 10배가 아님. 최근성 버킷 경계 |
| `place.mjs` | 멀티 디스플레이 · 화면 밖 방지 (whenwork 테스트 승계) |
| `manifest.mjs` | 깨진 JSON · 없는 필드 · 모르는 `protocol` 버전 → 그 파일만 건너뜀 (LINK-05) |
| `platform.test.mjs` | darwin · win32 구현이 같은 모양인지 계약 검사 (PLAT-01) |

CI는 두 OS에서 돈다. 형제 앱은 Windows만 돌렸지만 이 앱은 양쪽을 낸다(REL-01).

## 10. 결정 기록

새 결정은 여기 `D-nn`으로 남기고 **폐기안도 함께 적는다.**

### D-01 스택은 형제 앱 계열이다
Electron 43 · 바닐라 JS · `node:sqlite` · electron-builder · 미서명 배포. 여섯 번째 앱이 스택을 바꾸면 시리즈가 갈라진다. **폐기안:** Tauri 2 — 상주 메모리가 앱당 40~80MB로 Electron의 1/3이고 런처는 상시 상주라 매력적이었다. 그러나 형제 앱의 `platform/`에 쌓인 실패 지식(미서명 로그인 항목, 트레이 숨김 영역, 단축키 조용한 실패)을 Rust로 다시 밟아야 하고, 시리즈에서 이 앱만 이질적인 스택이 된다. 렌더러가 바닐라라 이식 자체는 쉬웠다는 점만 기록해 둔다.

### D-02 자기 명사를 갖지 않는다
할 일·메모·일정·소리·사람 중 무엇도 만들지 않는다. 저장하는 것은 랭킹뿐이다. 이 앱이 데이터를 갖기 시작하면 형제 앱과 기능이 겹치기 시작한다 — `store.mjs`가 100줄을 넘으면 경고 신호다.

### D-03 형제 앱이 하나도 없어도 온전히 동작한다
사용자가 다섯 앱을 전부 쓰지 않고 필요한 것만 골라 설치한다(2026-09-19 확인). 따라서 앱 실행·파일 열기·계산·스크립트만으로 v1이 성립해야 하고, 연동은 **더해지는 것**이지 전제가 아니다. `~/.when/apps/`가 없으면 오류도 안내도 없이 그냥 넘어간다(LINK-01). 반대 방향도 같다 — 형제 앱은 이 앱이 없어도 그대로 동작한다.

### D-04 연동은 파일 기반 수동적 발견이다
형제 앱이 `~/.when/apps/<id>.json`을 떨어뜨리고 WHENCOMMAND가 읽는다. **폐기안 ①** 각 앱의 SQLite를 직접 읽기 — 스키마가 바뀔 때마다 이 앱이 깨지고, 다섯 앱의 스키마를 이 앱이 알아야 한다. **폐기안 ②** 앱이 실행 중일 때 소켓으로 등록 — 앱이 꺼져 있으면 명령이 목록에서 사라져 "있다가 없다가" 한다. 파일은 앱이 꺼져 있어도 남는다.

### D-05 단축키만은 OS별로 다르게 둔다
macOS `⌘Space`, Windows `Alt+Space`. 형제 앱은 두 OS에 같은 조합을 일부러 썼지만(손가락을 다시 안 배우게), **이 앱은 시리즈에서 가장 자주 누르는 키**라 각 OS의 관례를 따르는 편이 이익이 크다 — macOS 사용자는 `⌘Space`에 이미 손이 가 있고(Spotlight), Windows는 `Alt+Space`가 PowerToys Run의 자리다. **폐기안:** `Ctrl+Alt+<글자>` 통일 — 형제 앱과 일관되지만 세 손가락이고, 남은 글자가 마땅치 않았다(`C`는 WHENCALENDAR가 쓴다). 대가는 [PLAT-03·04](02_요구사항.md#플랫폼-plat)의 충돌 안내다.

### D-06 창은 미리 만들어 숨겨 둔다
`show()`/`hide()`만 하고 `close()`하지 않는다. 매번 `BrowserWindow`를 만들면 렌더러 초기화에만 수백 ms가 들어 120ms 예산(PANEL-02)을 못 지킨다. 대가는 상주 메모리인데, 어차피 트레이 앱이라 이미 떠 있다. **(2026-09-19 실측)** 미리 만든 창 27ms vs 새 창 133ms로 확정. 설치 직후 첫 실행의 첫 페인트만 446ms(콜드 캐시)라, 시작 직후 한 번 보이지 않게 그려 두는 워밍업은 넣되 그 이유를 이렇게 적어 둔다(§11 #6).

### D-07 확장은 셸 스크립트다
`~/.whencommand/scripts/`의 실행 파일이 곧 명령이다. **폐기안:** Raycast식 JS 확장 API — 만드는 순간 그 API가 제품이 되어 문서·버전·샌드박스·심사가 따라온다. 1인 사용자에게 셸 스크립트가 같은 일을 하고 비용이 0이다. 스크립트가 부족해지면 그때 다시 본다.

### D-08 입력줄은 화면 위 28% 중앙이다
WHENCALENDAR가 상단 중앙, WHENMUSIC이 우하단을 쓴다. 28% 지점은 상단 아일랜드 아래이고, `whenwork/main/place.mjs`의 `centerY:false`가 정확히 이 값이다 — 복사해 쓴다. 순간적으로만 뜨므로 WHENCALENDAR와 잠깐 겹쳐도 허용한다.

### D-09 파일 검색은 OS 인덱스에 위임한다
macOS `mdfind`, Windows Search. **폐기안:** 자체 인덱서 — 두 OS가 이미 커널 수준에서 같은 일을 하고 있어 배터리와 디스크를 두 번 쓴다. Everything SDK는 Windows에서 훨씬 빠르지만 사용자가 별도 설치해야 해 "설치 파일 하나로 끝"에 어긋난다. 인덱스 품질 문제는 OS 설정으로 푼다(FILE-05가 그 사실을 알린다).

### D-10 랭킹은 frecency다
`base × (1 + log1p(hits) × recency)`. 곱셈이라 매칭 0이면 결과도 0이고, `log1p`라 새 항목이 영영 묻히지 않는다. 최근성은 연속 감쇠 대신 4단계 버킷 — 예측 가능하고 테스트하기 쉽다. **폐기안:** 단순 사용 횟수 정렬 — 한 번 많이 쓴 앱이 영원히 1위에 고정된다.

### D-11 공급원은 비동기로 합류한다
빠른 공급원(앱·계산·스크립트·형제 앱 명령)은 캐시에서 즉시 답하고, 느린 공급원(파일)은 늦게 도착해 `query:more`로 합류한다. 전부 기다렸다 한 번에 그리면 타이핑이 막힌다(SRCH-08). 늦게 온 결과가 이미 고른 항목의 자리를 밀지 않도록, 도착 시점에 선택 중인 항목은 위치를 유지한다.

### D-12 규약은 별도 저장소에 둔다
`when-protocol` — 매니페스트 스키마·예제·각 앱이 붙이는 법. 여섯 앱 어느 쪽에도 두지 않는 이유는, 어느 한 앱에 두면 그 앱이 나머지의 상위가 되기 때문이다. 규약은 코드가 아니라 **구조**라서 "코드를 공유하지 않는다"는 원칙과 충돌하지 않는다.

### D-13 macOS를 1급으로 낸다
지금까지 다섯 앱은 Windows가 주였고 `platform/darwin.mjs`에는 "실기기에서 검증되지 않았다"는 주석이 남아 있다. 이 앱은 macOS에서 개발되므로 양 OS를 동등하게 내고, 미검증 항목 셋을 실측해 형제 앱에 돌려준다(DONE-05).

### D-14 여섯 앱은 코드를 공유하지 않는다 (WHENMUSIC D-17 승계)
2026-09-19에 형제 앱의 중복을 실측해 이 결정을 재확인했다.

|---|---|---|
| 100% 동일 | `settings`(42) `queue`(98) `place`(30) `platform/index`(12) `index`(8) | **190줄** |
| 89~98% | `update`(181) `platform/darwin`(71) `platform/win32`(49) | 301줄 |

### D-15 결과 종류는 출처 칩으로 드러낸다 (2026-09-19)
`design/mockups/panel-options.html` §1의 다섯 안을 비교해 **㉤ 출처 칩**을 채택했다 — 행 40px · 폭 560px · 최대 8줄 · 하단 바 34px. 출처는 각 줄 오른쪽 끝 알약으로 세우고, 형제 앱만 `--accent` 색점, 스크립트는 `--success`, 앱·파일은 `--text-muted`. **폐기안 ①** ㉣ 종류별 머리글 — 출처가 가장 명확하지만 순위를 종류에 종속시켜 frecency(D-10)를 무력화하고, 느린 공급원이 합류할 때(D-11) 목록이 통째로 재배치된다. **폐기안 ②** ㉠ 두 줄 행 — 부제에 출처가 글자로 섞여 훑을 때 안 보이고 8줄에 406px을 쓴다. **폐기안 ③** ㉡ 입력줄 분리 — `BrowserWindow`가 둘이라 120ms 예산(PANEL-02)에 불리하다.

### D-16 설정은 별도 작은 창이다 (2026-09-19)
입력줄은 순간적이어야 하고(뜨고 → 한 줄 → 사라진다) 설정은 머무는 화면이라 성격이 다르다. 540px 창 하나에 단축키·시작·스크립트·형제 앱·데이터·정보 여섯 섹션. 이 앱의 **유일한 창**이고, 형제 앱 연동 상태(연결됨·설치 안 됨·매니페스트 오류)를 사용자가 볼 수 있는 유일한 자리다. **폐기안** 입력줄 안에서 설정 모드 — 순간적인 창에 머무는 화면을 넣으면 `Esc`·포커스 이탈로 닫히는 규칙(PANEL-05)과 충돌한다.

### D-17 스크립트 출력은 길이로 가른다 (2026-09-19)
stdout 3줄 이하 + exit 0이면 **자체 토스트**(우상단 4초, 한 줄이면 자동 복사). 그 밖은 **같은 패널이 아래로 자라** 고정폭 출력을 보인다. 실패(exit ≠ 0)는 stderr 원문과 `경로:줄번호`를 그대로 보이고 조용히 지나가지 않는다(EXT-05). **폐기안** OS 알림 — 권한을 묻고, 알림 센터에 쌓이고, 두 OS 모양이 달라 "같은 앱"(DONE-03)이 깨진다.

## 오픈이슈

1. **형제 앱에 딥링크를 붙이는 순서** — 다섯 앱 모두 `setAsDefaultProtocolClient`가 없다. WHENCOMMAND v1이 나온 뒤 한 앱씩 붙일지, 먼저 한 앱(WHENNOTE)에 붙여 규약을 검증하고 나머지를 따라가게 할지. 후자가 안전해 보이나 WHENCOMMAND가 그만큼 늦어진다
2. **라이브 조회(`mode: "live"`)** — 형제 앱의 검색 결과를 입력줄 안에서 보여 주려면 딥링크로는 부족하고 양방향 IPC가 필요하다. 로컬 소켓 대 파일 기반 요청·응답 중 어느 쪽이 "앱이 꺼져 있어도 조용히 실패"라는 성질을 지키기 쉬운지 미정. v2
3. **`⌘Space` 안내의 한계** — Spotlight 단축키는 사용자가 시스템 설정에서 직접 꺼야 하고 앱이 대신 해 줄 수 없다. 첫 실행 안내로 충분한지, 아니면 기본값을 다른 조합으로 두고 `⌘Space`를 권유만 할지. **(2026-09-19 해소)** Spotlight를 켜고 재면 **둘 다 뜬다** — 막을 방법이 없으므로 안내가 유일한 길이고 기본값은 `⌘Space`로 유지한다(D-05). 다만 `register()`가 true여도 Spotlight가 함께 뜨므로 **PLAT-02의 "등록 실패가 드러난다"는 반환값만으로는 부족**하다 → 첫 실행에 "지금 눌러 보세요" 단계를 두고, 눌렀을 때 Spotlight도 떴는지 사용자에게 묻는 흐름(§8 ②)을 확정. 앱이 Spotlight 상태를 직접 읽는 건 `defaults read com.apple.symbolichotkeys`의 64번 항목으로 가능하다 — 안내를 띄울지 판단하는 데만 쓴다
4. **아이콘 추출 비용** — 앱 수백 개의 아이콘을 시작할 때 전부 뽑으면 첫 실행이 느려진다. 지연 로딩 대 캐시 파일 중 어느 쪽인지 미정
5. **앱 아이콘·트레이 아이콘** — **받음(2026-09-19).** ⌘ 매듭, 파랑→보라 그라데이션, 어두운 둥근 사각 배경 — 시안 §7의 ⌘ 자리표시자와 같은 발상. 원본은 `assets/icon/whencommand.png`에 두고 `tools/make-icon.mjs`(WHENWORK 방식: 원본을 줄이고 글리프만 떼어냄)로 `build/icon.png`(512)·`build/tray.png`(32)·`build/tray@2x.png`(64)·`build/tray-Template.png`(macOS 단색)를 굽는다. 트레이용 단색 글리프는 그라데이션을 버리고 ⌘ 모양만 흰색/검정으로 — Template 이미지는 OS가 칠한다
6. **단축키를 뒤늦게 뺏기는 문제** — 실측 #4에서 Carbon 핫키는 **나중에 등록한 앱이 이긴다**는 것이 확인됐다(Raycast가 쥐고 있던 `⌘Space`를 POC가 가져갔다). 그러면 우리가 떠 있는 동안 Raycast·다른 런처가 (재)시작하면 `⌘Space`가 조용히 그쪽으로 넘어가고, 우리 쪽에선 아무 오류도 나지 않는다 — 형제 앱이 걱정했던 "true인데 안 눌림"의 실제 경로일 가능성이 크다. 후보: ① 일정 주기로 `unregister`→`register` 재등록, ② N분간 발화가 없으면 재등록, ③ 트레이 메뉴에 "단축키 다시 잡기". 어느 것도 완전하지 않아 미정
7. **영문 앱의 한글 별칭** — 스모크에서 `ㅋㄹ`이 0개였다. 초성 검색은 한글 이름에만 걸리는데 macOS 앱 이름은 거의 영문이라, 사용자가 "크롬"이라 생각하는 앱을 초성으로 못 찾는다. 후보: ① `ko.lproj/InfoPlist.strings`의 현지화 이름을 함께 색인(있는 앱만 해결), ② 작은 별칭 표(크롬→Chrome, 사파리→Safari, 터미널→Terminal…)를 내장, ③ 사용자가 고른 기록으로 별칭을 학습(`ㅋㄹ` 치고 Chrome을 고르면 다음부터 연결). ③이 이 앱의 성격(저장하는 건 랭킹뿐)과 가장 맞지만 첫 번은 못 찾는다
